login · verify — errors and waits

kebi-app · app/(auth)/login.tsx + verify.tsx · kebi-auth-flow.md · applies the kernel

These two are the app's best-handled screens already: an in-flight "sending code" with a spinner, a shake for invalid input, inline messages rather than toasts (correct — a toast on a keyboard-covered screen is invisible), an expired-code path and a 60s resend cooldown.

What's missing is what happens when the problem is not the user's input: no connection, or the provider being down. Today both fall through to the same generic line, which invites the user to keep retyping an address that was never wrong. There is also no empty or loading state to design — nothing is fetched before you sign in — so this file is about the failure vocabulary only.

1 · login your fault, or ours?

The shake is for input the client can reject locally. Everything that comes back from the network needs to say whose problem it is, because the recovery is completely different: fix the address, or wait.

2 · verify three different wrongs

The code screen has three failures the code already distinguishes internally (expired, an invalid code, and rate limiting) — the question is whether the copy does too, and what the boxes do while it checks.

Shake + red boxes, and the copy carries the most common actual cause: they typed an older code from a previous message. The digits stay so the user can see what they entered — clearing them is the fastest way to make someone retype a correct code wrongly.

Expiry is not a typo — warn tone, boxes cleared (the code is dead, keeping it invites another attempt with it), and the cooldown is skipped: the resend button is the primary action, because waiting 47 seconds to fix our expiry is our problem, not theirs.

recommended

Rate limiting is a boundary, not a fault: warn-toned, boxes disabled rather than red, and the cooldown becomes the only path forward — no retry button, because there is nothing to retry until the clock runs out. Same rule as chat's daily limit.

login and verify, recommended

Keep everything that exists — the shake, the red field, the inline messages, the sending state, the cooldown. This screen pair was built right.

1b + 1c — split the network failures out of the generic line: offline is warn-toned and says the address is fine; a provider failure says "not you" and points at the social buttons. Neither shakes the field, because nothing the user typed is wrong.

2a–2d — four distinct outcomes with four sentences: "checking" while the auto-submitted code is in flight, a wrong code in red keeping the digits, an expired code in warn with the boxes cleared and the cooldown waived, and rate limiting in warn with the countdown as the only way forward.
