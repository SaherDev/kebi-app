boot · dead routes — the two states with nowhere to live

kebi-app · app/_layout.tsx + components/splash.tsx + the missing +not-found · applies the kernel

Two edges that belong to no screen. First, the splash holds for a fixed 2.6s and hands off to home regardless — so a session restore that takes longer, or fails, lands the user on a home screen that quietly can't fetch anything, or bounces them to login. Second, there is no +not-found route: any URL that doesn't match renders expo-router's stock "Unmatched Route" screen — framework chrome, in a app that otherwise never shows any.

The second one is not hypothetical: +native-intent.ts exists specifically to redirect one such URL away from that screen.

The splash is a fixed timeline, not a progress bar — by design (§ performance budgets: splash to home, 2.5s max, regardless of network). The question is only what the user sees when auth hasn't resolved by the time it ends.

boot and dead routes, recommended

1b + 1c — the splash holds while auth is unresolved instead of handing off on a timer, using the loading screen the design system already specifies (mascot, cycling status at 5s, a way out at 15s). The failure says "your places are safe", because a failed boot is when a user most fears otherwise.

2b + 3b — add the +not-found route the app has never had, one sentence and one way home, no retry. The action is the borderless text action the toast and the error row already use, not a button: same vocabulary for every recovery in the app, and no bordered box on a screen that exists to say "nothing here". This applies to all three dead ends — a gone place, a gone area, an unmatched route — so the two already shipped get updated with it. Keep redirectSystemPath doing its one specific job rather than swallowing every bad URL, so a broken link shape stays visible instead of silently becoming a home screen.
