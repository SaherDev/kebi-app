chat — five ways to draw an area link

Venues in a turn get two affordances: a semibold name in the sentence and a chip in the rail beneath it. Areas get neither — toRailEntities filters them out and, inline, chat-answer.tsx renders a link with the exact classes it gives **bold** (font-semibold text-text). So today an area is invisible as a destination, and so is a venue until you reach the rail. Now that kebi://area/{key} opens a real screen, that has to change. All five below render the same turn — the monday-in-canggu answer, one area and three venues — and differ only in how the area is drawn.
a · leave it
the area stays exactly what it is now — a semibold word, tappable, no rail slot. zero work, the sentence stays a sentence. indistinguishable from bold; nobody discovers it.

The thing all five sit on top of

  • Inline, chat-answer.tsx gives a link and **bold** identical classes. Whatever is chosen for areas, a venue link inline is equally undiscoverable — the rail is currently carrying the entire affordance. Worth deciding at the same time.
  • The rail chip already has an area branch it never reaches: CHAT_ENTITY_FALLBACK_ICON is keyed by kind, and toRailEntities drops every area before it can be used.
  • b and d compose. They answer different questions — b makes the word in the sentence openable, d gives the turn an index. Picking both is coherent; picking c and d is not.

Still open

  • Which area, when there are three. e needs one, and a turn comparing Canggu with Seminyak has no single setting.
  • Rail label. "mentioned" survives a mixed rail; "places" does not.
  • Order in a mixed rail. Areas first reads as scope-then-detail; mention order is what the current code promises.
