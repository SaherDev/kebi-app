my notes — loading, empty, error

kebi-app · apps/mobile/src/app/my-notes.tsx · insider-only · applies the kernel

This screen is load-bearing: the write flow has no receipt and no review step, so it is the only place an insider can ever see what their prose became. Which makes its failure state the worst one in the app — myClaims.loadFailed renders as a single grey sentence with no retry, and the honest reading of it is "your notes are gone".

It also has a state no other screen has: the capability check. While curate is unresolved the screen returns a bare top bar and null — a blank page that means "deciding whether you're allowed in here", which looks identical to a blank page that means "loading" and to one that means "you've written nothing".

Long-press → remove is optimistic: the note disappears at once, a 5s toast holds the undo, and the count in the subtitle drops with it. If the write fails the note comes back where it was and the toast becomes "couldn't remove that one". Already the design system's rule for destructive actions — nothing new here.

my notes, decided

1b + 1c — the hero never waits (it's static text), the count subtitle and the notes shimmer in the quote-rail shape, and the capability wait looks exactly like the data wait minus the write button. The user should never be able to see that a permission check happened.

2b — one ghost note under a faded anchor, plus a ✎ write row. It's the only way to answer "what is a note?" before the first one exists, and it matches the ghost language on home and library.

3b — frozen notes under a retry line, with the extra clause "they're still there — this is the list, not the writing". Everywhere else "nothing lost" is enough; here the user's fear is specific, so the sentence is specific.
