settings — loading, error

kebi-app · apps/mobile/src/app/settings.tsx · ADR-054 · applies the kernel

Settings has no empty state (every row always exists) but it does have the most dangerous failure in the app. The screen re-reads getUserSettings on focus, and the catch block does this:

// Non-fatal: the rows fall back to "not set" rather than blocking

So a failed read renders "not set" next to "about you" and "getting around" — for a user who filled both in months ago. It isn't a missing state, it's a wrong statement about their data, and the obvious response is to go and re-enter everything.

1 · opening settings the rows exist — only their values don't yet

Two reads land here: the profile (name, email, plan) and the settings summary (whether about-you and getting-around are filled). Both are fast, and neither should ever move the layout — the rows are fixed furniture.

Frozen value skeletons plus a toast — closest to the kernel's letter. But the toast disappears after 5s and leaves two permanently grey stubs with no explanation, and a user who arrives after the toast has faded learns nothing. The inline line in b persists as long as the problem does.

settings, decided

1b — static furniture never shimmers. Only the avatar, name, email and the two status values do, and every row stays tappable while they load. The screen must never render "add your name" or "not set" as a loading state — those are answers, and we don't have them yet.

2b — the failed read shows — plus one persistent warn line: "couldn't check these. your answers are safe." Delete the silent setSettings(null) fallback; distinguish unknown from not set in the state, not just in the copy.

This is the clearest instance of the rule area produced: never let "empty", "failed" and "still loading" collapse into the same pixels. Here they collapse into the same two words — and those words happen to be a claim about the user's data, which makes it the one worth fixing first.
